# BoxHockey (PuckTastic)

**This repo is PuckTastic, a pack of puck games, since 2026-10-24: read "Pack structure" below first.** Most sections after it were written when the repo was Box Hockey alone and name its old paths (`src/app/game.tsx`, `src/app/loadout.tsx`, `src/components/...`); that section's "Where the old paths went" maps them.

Physics-driven tabletop box hockey against the CPU or a friend across the table (Expo/React Native, Skia-rendered). Store name PuckTastic (BoxHockeyTastic until 2026-10-24). Part of the `@rific`/`@tastic`/InfiniteToken app ecosystem - depends on `@rific/auto-paper`, `@rific/feedback-press`, `@rific/focus-chain`, `@rific/splash-gate`, `@rific/toaster`, `@rific/updater`, `@tastic/sprites` (the `./gravity` subpath only, for the gravity-well particle-swirl visual - see `src/components/GravityWellMarker.tsx`), `@tastic/core`, `@tastic/hud`, `@tastic/input`, `@tastic/physics`, `@tastic/profile`, `@tastic/shell`, `@tastic/split-screen`. The gravity well's *force* math (`applyGravityWells`, bounded quadratic falloff) stays in `@tastic/physics` - only the cosmetic particle-swirl rendering moved to `@tastic/sprites`; the two packages compose at this app's own call sites, neither depends on the other.

**Expo has changed.** Read the exact versioned docs at https://docs.expo.dev/versions/v57.0.0/ before writing any code - don't rely on general Expo knowledge, this app is on SDK 57 specifically.

## Pack structure (PuckTastic, 2026-10-24)

App Review flagged LightCycles, Snake and Solitaire as spam (too many similar apps), so Jay is folding the fleet into packs. PuckTastic is BoxHockey's own App Store record (`com.infinitetoken.BoxHockey`, BoxHockey 1.0 already released), grown into four games in Home's order: **Box Hockey** (the star), **Air Hockey** (from the AirHockey repo), **Paddles** (Pong with a puck) and **Breaker** (Pong's bricks, plus a round alone). Soccer may come later. All four ship in 2.0. The plan doc (decisions, the 3-day cut, what's left) is https://claude.ai/artifact/NDpksPYUmoJrJ7dRjs3Aet.

**Layout.** The registry is meant to fit the later packs too (DuelTastic, CardTastic).
- `src/app/`: thin routes only, each rendering one of `@tastic/shell`'s screens (`_layout` its `RootLayout`). `index` (Home), `profiles`, `stats`, `loadout/[game]`, `play/[game]` (both with `generateStaticParams` over `games`, so the static web export has a page per game).
- **The game id comes second in a route, never first** (2026-10-25; they were `[game]/loadout` and `[game]/play`). expo-router strips the web build's base path off the front of an in-app link as well as the address bar (`stripBaseUrl` in its getStateFromPath), so under `WEB_BASE_URL=/boxhockey` the link to `boxhockey/loadout` lost its first segment and landed on `/loadout`, "Unmatched Route": tapping Box Hockey on Home did nothing useful on the web build, while the other games worked (found and checked on a local web export, 2026-10-25). Native never had a base path, so it was web only. DuelTastic (the LightCycles repo) has the same fix, for `lightcycles` under `/lightcycles`. Since 2026-11-11 both packs serve under their own name (`/pucktastic`, `/dueltastic`), so no game id matches the path any more; the rule stays.
- `src/pack.ts`: the pack's `PackDefinition` and its one store. Its identity (`name`, `wordmark`, `colorCaption`), `games` in Home's order, and the options the shell reads through `usePack()` (2026-10-28): `seatColors` (red P1 `#f44336`, blue P2 `#2196f3`: the theme's primary and secondary and a fresh install's guest and CPU colors), `HeroTitle` (from `src/hero/`) and `otaVersion` (from `src/constants/release.ts`, which stays put for the OTA tooling, for Settings' version label). It sets no `appearance` (the theme follows the system's), `fonts` or `fontFamily` (Paper keeps its own font); DuelTastic sets all three. The store is `createPackStore(pack, { keyPrefix: 'pucktastic:', migrate })`, which merges the games' reducers and builds the shell's from `seatColors` and `appearance`.
- `src/hero/HeroTitle.tsx`: the pack's hero (the wordmark stacked in `MONO_FONT`, goal-line bars in the players' colors, the bouncing puck), on the shell's `HeroTitleProps` (`words`, `color`, `p1Color`, `p2Color`, `active`). It ignores `active` (false while Home is covered or the app is in the background), so the puck keeps bouncing as before.
- **The shell is `@tastic/shell`** (since 2026-10-29, step 4 of DuelTastic's TODO.md `@tastic/shell` plan; its source is `../React-Native-Game-Shell`, so read its README and `.claude/CLAUDE.md`): `RootLayout` (providers, gates, `GuideHost`, the stack), the screens (`HomeScreen`, the loadout, `StatsScreen`, `ProfilesRoute`, `LoadoutRoute`/`PlayRoute`), `SettingsDialog` (app-wide settings only), the `GameDefinition` and `PackDefinition` contracts, the store (`createPackStore` and the shell's slices), and what a game builds on (`createPlayerSettings`, `createGameStats`, `createGameGuideSlice`, `useActiveRound`, `useProfiles`, `safeBack`). `src/app/`, the games, `src/shared/`, `src/hero/` and `importBoxHockey1.ts` import it all from its one barrel, `'@tastic/shell'`. Until then it was `src/shell/` here, byte-identical to DuelTastic's since 2026-10-28, with `src/shared/playerSettings.ts` and `gameStats.tsx` beside it. All three are the package's now, and so are their tests (the shell's own `appSettingsSlice`, `createPackStore` and `profiles`, `playerSettings.test.tsx`, and `statusBar.test.tsx`'s check that the shell's Theme turns auto-paper's status bar off; its source scan stays here) and the two UI sounds every button plays (`assets/sounds/notification.wav`, which nothing else here used, is gone; `select.wav` stays for Box Hockey). **A change to the shell goes into the package**, released by tag, and reaches each pack with a version bump (`npm install @tastic/shell@^x.y.z`). To try one in a pack first, install a packed tarball with `npm install --no-save` (the package's CLAUDE.md), never `yalc push`.
- `src/shared/`: code two or more games use, imports no game. `PlayerRankings`, `SeatResultCards`, `SeatToasters`, `useUnlockToasts`, `useGameSound`, `lazySkia` (every board's web host), `controlScheme`, and `paddleGame/` (Paddles' and Breaker's one engine).
- `src/games/<id>/`: each game, exported as one `GameDefinition` from its `index.ts`.
- **Every piece of code lives in one place. Shared code never imports a game (nor does the shell, a package), and a game never imports another game.** `eslint.config.cjs` enforces it for `src/shared/` and each game with `no-restricted-imports` (a game may import itself). A game hands the shell what it needs through its `GameDefinition`: store reducers, a Provider (its stats context), `useLoadout(mode)` (its match options, seat controls and CPU difficulty for the shared loadout), `PlayScreen`, `StatsSections`/`AchievementList`, `resetStats`, its How to Play (`guide`), its `seatTwo` choices and `twoPlayerSeats`.

**Saved data (decided now, for good).** The store is saved under `pucktastic:root` (keyPrefix `'pucktastic:'`). Each game keeps its own store keys, named for it: `<id>Settings`/`<id>Controls`/`<id>Achievements`/`<id>Guide` (`boxhockey`, `airhockey`, `paddles`, `breaker`); settings and controls are per player (see "Loadouts follow the player" below). Pack-wide: `appSettings` (Edge Guard; Lock Orientation and its angle until shell 0.5), `opponent` (seat 2), `profileSelection` and `seatColors` (action namespace `'pack'`), theme, haptics, sound, Keep Awake and profiles; `liveplay` is never persisted. Stats and achievements stay separate per game. **A BoxHockey 1.0 save is imported once** (Jay, 2026-10-24: clean names, without dropping his earliest players). `src/importBoxHockey1.ts`, the persistConfig's `migrate` in `pack.ts`: on the first launch of a pack build (no `pucktastic:root` yet), a `boxhockey:root` save is copied over under the pack's names. `theme`, `haptic`, `sound`, `keepAwake`, `profiles`, `profileSelection` and `seatColors` keep theirs; `achievements` and `guide` become `boxhockeyAchievements` and `boxhockeyGuide`; 1.0's one `settings` becomes seat 1's player's own `boxhockeySettings` (the profile 1.0 had in seat 1, or seat 1's guest), minus the fields that are the pack's now (Lock Orientation, its angle and Edge Guard go to `appSettings`, the last mode picked on 1.0's Home to `opponent`, 2 Player as a person and anything else the CPU, and each seat's shot style to the player in that seat); and 1.0's `profileExtensions` (each profile's own shot style, which wins over the one it inherited from its seat) go to `boxhockeyControls`. Every later launch finds the pack save and does nothing. The 1.0 save stays in storage, unread from then on; an unreadable one starts fresh. **It's temporary:** delete the file and the `migrate` once nearly everyone is past 1.0, no earlier than six months after 2.0 ships and not before May 2027 (`TODO.md` has the steps); a 1.0 player who skips every update until then starts fresh. A `persist:root` save is never read, and pre-1.0 players are no longer grandfathered past Box Hockey's cards, so the older notes on `LEGACY_STORAGE_KEYS` and `createReturningPlayerMigrate` below no longer apply. **Seat 1 and seat 2.** Seat 1 is picked on Home (Solitaire's player button) and starts every loadout. Seat 2 is player 1's to pick (`@tastic/shell` 0.7, Jay 2026-11-07): an opponent button beside seat 1's in each loadout lists the CPU at a difficulty, Solo (Breaker only, seat 2 empty, saved as `'nobody'`; it said Nobody until then, and Breaker's Play Alone card now says "Pick Solo, then clear every brick...", for Jay to review) and Player, each kind behind a divider, never a profile, and carries the CPU's Color row. A game without Nobody reads a saved Nobody as the CPU. The CPU's difficulty is per game, and seat 1's player's.

**Loadouts follow the player** (Jay, 2026-10-24: "ALL the loadout settings should follow the player... the one exception is the player 2's settings, optional override color, and their chosen control scheme"). `@tastic/shell`'s `createPlayerSettings({ id, defaults, distinctControls? })` is every game's settings: `<id>Settings` holds each player's own changes to the match settings (CPU difficulty and tilt steering included), loaded whenever that player is seat 1, over the game's `DEFAULT_SETTINGS` (so a field added later starts at its default); `<id>Controls` holds each player's controls (Box Hockey's shot style, the desktop keys elsewhere), loaded in whichever seat they sit, seat 2's only for a person. A player is a profile id, or `guest:1`/`guest:2` (the two seats' guests are different people). A seat's color pick already follows its profile (`seatColors`). Where two seats can't share a control (the mouse and key clusters: Air Hockey, Paddles, Breaker), a saved clash moves seat 2 to the next free one for the match, unsaved. Deleting a profile forgets both. A game's How to Play reads the same through `select(state)`, returned flat (`control1`/`control2`) for `GuideHost`'s shallow compare. Pinned by the package's own `playerSettings` test.

## Tooling

Onboarded onto the shared `@infinitetoken` config packages (`eslint-config`, `jest-config`, `tsconfig`) - previously hand-rolled its own `eslint-config-expo`-based config, `jest-expo`-preset-direct config, and `expo/tsconfig.base`-extending tsconfig (the same pattern documented in [Swirlio](../Swirlio/.claude/CLAUDE.md)'s and [LightCycles](../LightCycles/.claude/CLAUDE.md)'s CLAUDE.md, which this migration followed).

`npx expo install --fix` + `npm update` were run as part of this pass too (`expo install --fix` genuinely found something here - `expo`/`expo-updates` were a patch behind) - confirmed clean afterward: `npx expo install --check` reports up to date, `npm outdated` shows `Current === Wanted` for every dependency (remaining `Latest` values are all major bumps outside declared ranges, a deliberate-upgrade decision, not routine maintenance).

- `eslint.config.cjs` - `@infinitetoken/eslint-config/expo`, no local override (see below)
- `tsconfig.json` - `extends: "@infinitetoken/tsconfig/expo"`, keeps only the path-valued local bits (`paths`, `include`), plus two narrow `@shopify/react-native-skia` redirects (see below)
- `jest.config.cjs` - `@infinitetoken/jest-config/expo`, no options at all - `jest.setup.cjs` and `roots` are both auto-detected/defaulted (see below)

**`jest.config.ts` became `jest.config.cjs`, matching every non-Expo project in the fleet - no more `ts-node` gotchas.** This app (like every other Expo app) originally had `jest.config.ts` while every library/kit package used `.cjs` - a real divergence, not a justified one. `.ts` needed `import type {Config} from 'jest'` + a typed `const config: Config = ...` (a bare `export default createExpoJestConfig(...)` fails `tsc`'s declaration-emit check), plus a separate non-extending `tsconfig.jest.json` wired in via `TS_NODE_PROJECT=./tsconfig.jest.json` on `test`/`test:watch` (`ts-node`, Jest's `.ts`-config loader, can't resolve a tsconfig `extends` through a package's `exports` map at all). None of that exists for `.cjs` - plain `require()`, no transpilation, nothing to typecheck. Converting removed `tsconfig.jest.json`, the `TS_NODE_PROJECT` prefix on both scripts, and the `ts-node` devDependency entirely - see `@infinitetoken/jest-config`'s own README ("Why `.cjs`, not `.ts`") for the full history.

**`prettier.config.js` was deleted - `package.json` now has `"prettier": "@infinitetoken/eslint-config/prettier"` instead**, same as every library/kit package. The local file was a byte-for-byte duplicate of the shared package's own `prettier.cjs`; every Expo app had independently copy-pasted it rather than referencing the shared one.

**`metro.config.js` was deleted - it was unmodified `getDefaultConfig(__dirname)` boilerplate doing nothing.** Confirmed by removing it and running `npx expo export -p web`: builds cleanly, `canvaskit.wasm` still lands in `dist/` (copied into `public/` by the `setup-skia-web` postinstall script and served as a static file, fetched at runtime by `canvaskit-wasm`'s own init code - never `require()`d through Metro's bundler, so `resolver.assetExts` is irrelevant to it regardless). Swirlio never had this file at all and works the same way - this file's presence elsewhere in the fleet is boilerplate carried over from `expo customize`, not a requirement.

**`@shopify/react-native-skia` needs an explicit `paths` redirect to its compiled `.d.ts`, or typecheck fails inside the package's own source.** Identical root cause and fix as Swirlio: no `exports` map, `customConditions: ["react-native"]` follows the raw `src/index.ts`, which pulls in an upstream unused-`React`-import that only fails once `noUnusedLocals` turns on. Two `paths` entries redirect the bare specifier and the `@shopify/react-native-skia/src/web` deep path (`src/utils/loadSkiaWeb.web.ts` imports it directly to lazy-load the CanvasKit WASM runtime) to their compiled counterparts.

**Native/Expo module mocks moved from inline `jest.mock()` calls in `jest.setup.cjs` into individual `src/__mocks__/*.ts` files** - `react-native-reanimated`, `react-native-worklets`, `@expo/vector-icons` (+ its `createIconSet` deep import), `expo-splash-screen`, `react-native-gesture-handler`, `react-native-safe-area-context`, `expo-router`. This is a fleet-wide convention change, not BoxHockey-specific - see `@infinitetoken/jest-config`'s own CLAUDE.md for the full reasoning (manual `__mocks__/` mocking works fine under `jest-expo`, contrary to what that package's docs used to claim; `roots: ['<rootDir>/src']` is now a default there specifically so `src/__mocks__/` - not root `__mocks__/` - is where Jest picks them up, next to `src/__tests__/`). `jest.setup.cjs` now holds only genuine setup-file content (the `IS_REACT_ACT_ENVIRONMENT` flag and `unhandledRejection`/`uncaughtException` handlers; the RAF/cancelAnimationFrame polyfills and no-factory `NativeAnimatedHelper` automock also carried over at the time were removed on 2026-10-02 as no-ops, see Testing) and is auto-detected by `@infinitetoken/jest-config/expo` - no `setupFilesAfterEnv` option needed at all. Also renamed from `.ts` to `.cjs` - a later, separate cleanup: auto-detection genuinely supports either (a `.ts` setup file goes through Jest's own test transform same as any other `setupFilesAfterEnv` entry, unlike `jest.config.cjs` itself, which Jest loads directly before any transform exists), but once its content shrank to thin boilerplate with the mock factories gone, there was no remaining reason for this one hand-authored config file to use a different extension than every other one in the app - see `@infinitetoken/jest-config`'s README, "Why `.cjs`, not `.ts`." With the mock factories' `any` usage gone, `jest.setup.cjs` no longer needs its own `no-explicit-any` eslint override - `eslint.config.cjs` is back to the plain one-liner, same as Crumby. The one `any` this paragraph used to mention (bridging `requestAnimationFrame`'s polyfilled `NodeJS.Timeout` return type into `cancelAnimationFrame`'s DOM-lib `number` signature, under a targeted `eslint-disable-next-line`) lived in the RAF polyfill, which has since been removed as a no-op (see Testing) - `jest.setup.cjs` has no `any` left.

**Migrating onto `typescript-eslint`'s `recommended` ruleset escalated one pre-existing lint finding from warning to error.** `src/app/game.tsx`'s web keyboard handler used a ternary as a bare statement (`ready ? stableFaceoffReady(1) : stableFaceoffZoneTap(1, 0)`) four times - already flagged by base ESLint's `no-unused-expressions` as a warning under the old hand-rolled config, now also caught by `@typescript-eslint/no-unused-expressions` as an error (the old config never composed on `typescript-eslint.configs.recommended` at all). ## Triple Tap tip-off (2026-10-18)

Rebuilt to Jay's design: both players tap their own half `TRIPLE_TAP_TAPS` (3) times **in step** (a tap only counts while you aren't already ahead of the other player, `canTripleTap` in `useGameState.ts`; you can lead by one, then wait), then race to swipe. The swipe is judged exactly like a Flick shot (`resolveStrikeVelocity('flick', ...)`, so a stray extra tap never launches a dud). The first real swipe launches the puck off center at once (`TRIPLE_TAP_SWIPE`, swiper becomes `currentPlayer`, bookkeeping only). The other player's swipe within `TRIPLE_TAP_CLASH_WINDOW_MS` (250, first-pass, tune on a device) is added onto the moving puck with `combineAndClampVelocity` and knocks it off its line; later is too late. `TripleTapState` stays set (phase `simulating`) through that window so the trailing player's gesture and Board's latched ripple/streak survive the launch; `useTripleTap.ts`'s timer dispatches `TRIPLE_TAP_CLASH_END` to clear it.

- **Input:** a player's whole half (game.tsx's triple-tap views), live during the draw and, for the trailing player only, the clash window. The gestures key on those booleans, not `phase`, so the launch doesn't rebuild a drag in progress. `tripleTapKeys` remounts a zone's detector after EVERY release, counted or not (an ignored early tap changes no reducer state, and a still-mounted recognizer drops the next tap). Only a counted tap or a gate-passing swipe buzzes, so an ignored tap reads as "wait".
- **Visual:** no big circle any more (`tripleTapZoneCenter`/`Radius` and `TRIPLE_TAP_ZONE_RADIUS_RATIO` are gone). Each player's two rink face-off circles fill a little more per counted tap, ripple on each tap and breathe once all taps are in, with 3 tap pips between them; each swipe draws a streak from center.
- **CPU:** taps whenever a tap would count, after a reaction delay (so it follows the human in step), then swipes after reaction plus drag time; its swipe timer stays armed through the clash window, so a fast human can still get clashed.
- Tested in `tripleTap.test.ts` (lockstep, tap cap, swipe gating, launch, clash in and out of the window, CLASH_END, CPU swipes passing the gate, turn-alternation fuzz). **Not checked live on a device yet**, and the mode is touch-only (hidden on web), so a simulator or phone is the only way to feel it.

## Stick control (2026-10-18)

A fourth control scheme, `'stick'`, next to Flick (Flick stays the default; Jay wants to try Stick on a device first). The finger is the stick blade, and the shot is the contact, not a release: `src/utils/stick.ts` holds the pure physics, and the reducer runs it.

- **The hit** (`resolveStickContact`): the blade is a circle (`STICK_BLADE_RADIUS_RATIO` of the puck's radius, generous because the finger covers the puck), swept against the puck in the puck's own frame, so a moving puck and a moving blade both count. Along the contact normal (blade through the puck's center) the puck leaves at `(1 + STICK_RESTITUTION)` times the blade's approach speed, plus `STICK_CARRY` of the blade's sideways motion, clamped to `MAX_SPEED`. A square hit is a full shot, a glancing one a soft sideways one. An approach under `STICK_MIN_HIT_SPEED` is no hit. Finger points/sec convert to puck units with `STICK_VELOCITY_SCALE` (1/60: a puck unit is points per 60Hz step). All of these are first-pass values to tune by feel.
- **Where it runs:** `useGameState.ts`'s `stickSwing`, from `AIM_UPDATE` (which now carries `board`; `aimUpdate` passes `boardRef.current`) for a normal turn or a CPU intercept, and from `PHYSICS_STEP` for a human intercept (the finger arrives through `interceptTouch`), so a blade held still in a sliding puck's path deflects it. A hit goes straight to `'simulating'` like a flick release; an intercept hit also hands `currentPlayer` to the interceptor. The blade has to be clear of the puck at the start of a step to hit (`AimIndicator.stickClear` records "clear right now" for Board), so touching down on the puck does nothing until the finger leaves.
- **Missing is free:** releasing without a hit (`STRIKE`) is a whiff, back to `'idle'` on the same turn, with a fresh `puck` object so `useAIOpponent`'s turn effect (keyed on it) re-plans for a CPU that whiffed. A missed intercept just drops the `interceptAim`.
- **Walls and corners:** `clampBladeToBoard` keeps the blade (both ends of every step, touch-down included) inside the walls stepPhysics bounces off, rounded rink corners included. A puck against a wall or in a corner can't be hit from the wall side, only dug out from the open side; a hit into the walls bounces out with normal wall physics. Goal mouths, the center divider and gauntlet blocks are not walls for the blade (a real stick reaches over them).

- **Board:** no pulled-back stick, chevrons, front arrow or phantom puck for Stick. It draws the blade where it is (every preview tier) and, above `'off'`, a faint line from the puck straight away from the blade (where a square hit would go) while the blade is clear. `game.tsx` buzzes on the hit itself (`prevStickRef`) and skips the cancel-zone tick.
- **Fixed in passing:** `tryAimStart` clears `interceptTouchRef`, which was never reset, so a new intercept's first physics step folded in the previous drag's last finger position (for a Stick interceptor, a bogus swing across the board).

## Rink and Gravity physics (2026-10-18)

Found by replaying the real physics headlessly (an esbuild bundle of `stepPhysics`, `computeBoardLayout`, `planAIShot` and the face-off knock with a `react-native` Platform stub, the way `store/seed/generate.mjs` does it) on the iPhone 17 Pro Max layout (440x956, insets 62/34). Both fixes are in `src/utils/physics.ts` and pinned by `src/__tests__/gravityRink.test.ts`.

- **A puck behind a goal line beside the net could score (Rink only).** The pocket behind each line is open ice, so a puck resting there outside the posts is normal (face-off knocks end there often). But one sliding along just behind the line could rise into "not fully behind" by a fraction of a pixel with its center still outside the posts, carry its center into the goal's x-range on the next substep, and get shoved back past the line by the post (posts only skip a puck that is FULLY behind), which the score check read as a fresh crossing. About 2% of goals on Gravity or Classic with Rink were these, almost all the Hard CPU's: `planAIShot` replays `stepPhysics`, so it found and took them from exactly the reported spot. Fix: the score checks (in `stepPhysicsOnce` and `computeTrajectory`) use `cameFromBehindTop`/`cameFromBehindBottom`, which also count a puck whose CENTER was already past the line outside the goal's x-range at the start of the step. The posts and the one-way door still use `wasBehindTop`/`wasBehindBottom`. Checked: every goal this removes was one from beside the net, no goal through the mouth is lost, and Rink off is unchanged.
- **Gravity's center attractor could hold the puck forever at a low frame rate.** Its center sits on classic's divider; at a steady dt of about 1.25 or more (40 fps or slower) its pull on a puck touching the divider, bounced back at `WALL_RESTITUTION`, kept the puck above `STOP_THRESHOLD` every frame, so it looked still while 'simulating' never ended. Fix: `stepPhysics` splits any frame into steps of at most dt 1 (the wells, friction and `STOP_THRESHOLD` are tuned per 60 Hz frame). dt 1 and below play exactly as before.
- **Not the cause:** the corner repellers (`activeAtRest`) never kept a puck moving at that spot on any dt from 0.5 to 2.5; their reach ends before the back wall and the side wall. The physics alone doesn't explain the 30+ second wait itself (no never-ending state was found in the bottom-right pocket); the goal from behind the net does explain "came to rest there, then the next face-off". **Not checked on a device or simulator yet.**

`/game` keeps the screen from dimming and locking while it's up (`useKeepAwake('game')` from `@rific/core`, next to `useBackgroundPause`, released on unmount), unless the player turns off the Keep Awake row in Settings (default on, read live so the toggle applies mid-match). Audit F086: Expo only keeps the screen awake in development builds, and the OS auto-lock only counts touches (Pong's tilt steering never touches the screen).

- **The setting is core's, not this app's** (2026-10-17, when Keep Awake moved upstream): `@rific/core`'s `keepAwakeReducer` is mounted as `keepAwake` in `store.ts` (persisted like every key but `liveplay`; core's slice handles its own REHYDRATE under that namespace), and `Providers.tsx`'s `KeepAwakeBridge` (FeedbackBridge's shape: `initialValue` from the slice, `onChange` dispatching `keepAwakeActions.initialize`) mounts core's `KeepAwakeProvider` with `expoKeepAwake={ExpoKeepAwake}` (`import * as ExpoKeepAwake from 'expo-keep-awake'`). Handing it the module is what turns the feature on: without it `useKeepAwake` does nothing and hud hides the row. `useKeepAwake` drops both expo-keep-awake rejections (web refuses a wake lock in a frame without the Permissions-Policy, and rejects a release when none is held). - The row is `@tastic/hud`'s (0.23.0+): `BaseSettingsDialog` reads core's setting itself, with no props, and shows the row (caption "Stop auto-lock mid-match") only when `useExpoKeepAwake()` returns a module and the device is touch-first (native and touch-first browsers), like Lock Orientation. Needs `@rific/core` 0.4.0+.
- `expo-keep-awake` was already installed as a dependency of `expo`, so it is already in existing native builds; it's a direct dependency (`~58.0.3`). No new native build needed.
- Same in AirHockey, BoxHockey, LightCycles, Pong and Snake (the four with the shared `Providers.tsx` have the same `KeepAwakeBridge` byte for byte; Snake's sits next to its ScrollViewBridge), and in ArcheryDuel, Hangman, HexFleet and Solitaire. ## Status bar: per-screen options (2026-10-15)

The OS status bar is set through react-native-screens' screen options, never a `StatusBar` component. `_layout.tsx`'s `AppStack` (identical across AirHockey, BoxHockey, LightCycles and Pong) spreads `@tastic/core`'s `useRotationAwareStatusBar()` (0.14.0+) into the root Stack's `screenOptions`, which hides the bar while the content is rotated off portrait (no `locked` argument: `OrientationBridge` freezes the reading it follows), and /game hides it for the whole round through its own `Stack.Screen` options (`GAME_OPTIONS`, `{ statusBarHidden: true }`), set in the layout so they apply as the screen is pushed rather than one effect later. No style is passed: react-native-screens' default (`auto`, following the system appearance) is what expo-status-bar's `auto` gave before.

Why: an app linked against the iOS 27 SDK (Xcode 27) can't set the status bar through `UIApplication` any more (UIKit's `UIApplication.h`: setting it "does nothing if ... linked against SDK versions 27.0 or later"), and that is all React Native's `StatusBar`, and so expo-status-bar, does on iOS. `@tastic/core`'s config plugin now sets `UIViewControllerBasedStatusBarAppearance: true`, which react-native-screens needs, and under which every mounted `StatusBar` logs an `RCTLogError` (a red box in dev). So nothing may mount one: `<RotationAwareStatusBar />` (removed from core) and /game's `<StatusBar hidden />` are gone, `Theme.tsx` passes auto-paper's Provider `statusBar={false}` (0.13.2+, which also covers `Appbar.Header`), and expo-status-bar is no longer a dependency or an app.json plugin (its plugin did nothing without options). Pinned by `src/__tests__/statusBar.test.tsx` (no source file imports expo-status-bar or React Native's `StatusBar`) and, for the shell's Theme turning auto-paper's off, by `@tastic/shell`'s own test.

- **The hide only shows in a Release build.** In a dev-client (development) build, expo-dev-launcher inserts its own view controller above react-native-screens' stack, so the screens' status bar options never reach UIKit and the bar never hides there, rotated or on /game (see @tastic/core's CLAUDE.md, "Status bar: per-screen options"). Check it in a preview/production build or a local Release build.
- **It needs a new native build.** `UIViewControllerBasedStatusBarAppearance` only reaches Info.plist at prebuild, and the app.json plugin list changed too, so the fingerprint runtime version moves on: an OTA update from here on won't reach an older binary.
- Android gets the same options from react-native-screens (no Info.plist key there). Not checked on a device on either platform.

## Gesture callbacks leaked the game screen (2026-10-18)

react-native-worklets keeps a native strong reference (a Hermes GC root) to every `runOnJS`/`scheduleOnRN` target for as long as the calling worklet's serialized copy lives, and the copy is cached while the component holds its gesture. `game.tsx`'s gestures called the screen's own `stable*` callbacks that way, so the screen was never collected. They now call `scheduleOnRN(callWorkletCallback, key, ...args)`, with each key from `useWorkletCallback(stableX)` (`@rific/core` 0.5.0), so the gestures hold only a string key and the latest callback is looked up at call time. The gesture deps are the keys (stable for the component's life), so the tripleTapKeys detector remount per press is unchanged. Never hand `runOnJS`/`scheduleOnRN` a callback the same component also reaches its worklet from. The gestures use `scheduleOnRN` from `react-native-worklets` (2026-10-18), since `runOnJS` is deprecated in Reanimated 4; the key scheme is unchanged. JS only, so it can ship in an OTA. Not verified on a device.

- **Game pages:** each game's loadout and play pages carry its own title and blurb, so a search for that game can land on it, and both name the page Home opens (`gamePath`: its loadout, or play when it has none) as canonical, so search engines count the two as one. Stats and Profiles are `noindex`. An id the pack doesn't have (the export's own `[game].html`) gets Home's. Jay wasn't sure about these pages and went with it: drop them to the pack's metadata if they ever cause trouble.
- **Canonical links** are `https://games.infinitetoken.com` plus `EXPO_BASE_URL` (build:web's `WEB_BASE_URL`, which Expo inlines into the static render as well), so they follow the path the build is served under, `/pucktastic` since 2026-11-11.
- **The tab's title after load:** each route also draws `PageTitle` (`GamePageTitle` on the game routes), a web-only `<Head><title>` drawn deeper than `@tastic/shell`'s own in `Fonts.tsx` (the app's name), so it wins (react-helmet-async takes the last one; checked with expo-router's vendored copy). - **Left bare:** expo-router's own `_sitemap.html` and `+not-found.html`, which take no metadata.
- **Checked** on a local export (`WEB_BASE_URL=/boxhockey expo export -p web --clear`, written outside the repo): every page's tags, one `<title>` each, `lang="en"` (the default root HTML's). `seo.test.ts` pins the copy, titles and canonical links, and that every route exports its metadata.
